## 구현 시스템 (담당 파트)

- **캐릭터 소환 / 합성 (Merge)** — 같은 캐릭터를 합쳐 상위 캐릭터로 성장, 랜덤 배치 소환
- **골드 자동 수급** — 캐릭터별 골드 생산량 + 업그레이드 배율 계산, 주기적 갱신
- **JSON 세이브 / 로드** — 캐릭터 ID·위치·진행 상태를 JSON으로 직렬화, 앱 재실행 시 복원
- **미니게임 (2종)** — 제한 시간 내 아이템 획득 방식, 결과에 따라 메인 게임 스탯 강화
- **보스 스테이지** — FSM(enum + Coroutine) 기반 Phase 전환, 체력 조건별 공격 패턴 변경

## 기술적 고민

### 1. JSON 기반 캐릭터 배치 데이터 저장 및 복원

PlayerPrefs는 Vector3 같은 구조적 데이터를 저장하기 어려워, 앱 재실행 시 캐릭터 배치 상태를 복원할 수 없었습니다.

- 캐릭터 ID, 위치(Vector3), 해금 여부를 담은 **데이터 클래스를 설계**하고 JSON으로 직렬화
- `Application.persistentDataPath` 기반 파일 저장으로 기기 내 영구 보존
- 로드 시 저장 데이터를 순회하며 오브젝트를 동일 위치에 재생성하는 **복원 흐름 구현**
- 캐릭터 수가 늘어나도 데이터 구조를 확장하기 쉬운 저장 체계 확보

### 2. FSM 기반 보스 패턴 설계

보스의 행동이 많아질수록 if-else로 상태를 관리하기 어려워졌습니다.

- `enum BossState`로 상태를 정의하고, 각 상태를 **Coroutine 메서드로 분리**
- 상태 전환 시 기존 코루틴을 중지하고 새 상태의 코루틴을 시작하는 `ChangeState()` 구조 구현
- 체력 80% / 40% 기준으로 Phase가 전환되며 공격 패턴이 변경되도록 설계
- 이후 패턴 추가 시 새 enum 값과 코루틴 메서드만 추가하면 되는 확장 구조 확보

## 회고

**어려웠던 점**
- 캐릭터 수가 늘어날수록 저장 데이터와 런타임 오브젝트 상태가 어긋나는 문제가 발생했습니다. 단순히 저장하는 것에서 나아가, **로드 시 데이터를 기준으로 오브젝트를 정확히 복원하는 흐름**을 별도로 설계해야 한다는 것을 깨달았습니다.
- 3인 팀 프로젝트였기 때문에 각자 작업한 부분이 충돌 없이 연결되려면 역할 분담과 인터페이스를 미리 정의하는 것이 중요했습니다.

**배운 점**
- 기능 구현 전에 데이터 구조와 오브젝트 생성 흐름을 먼저 정의하는 것이 유지보수와 확장에 중요하다는 것을 배웠습니다.
- FSM 구조를 처음 적용하면서 상태 기반 설계가 복잡한 행동 로직을 다루는 데 효과적임을 경험했습니다.
- 팀 프로젝트에서 Git을 통한 버전 관리와 코드 충돌 해결을 처음으로 경험했고, 이후 모든 개인 프로젝트에서도 Git을 활용하게 됐습니다.
- 기획부터 출시까지 전 과정을 경험하면서 게임 개발의 전체 흐름을 파악할 수 있었습니다.
